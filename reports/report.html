Main finding: correct arithmetic still needs correctly attributed inputs.

The rent calculator matched an independent exact-arithmetic reference on 165 of 165 fresh synthetic cases. However, an adversarial tool call could label a historical monthly amount as weekly by borrowing a valid quote about the proposed rent. The literal quote check accepted it.

The implication is narrow but material: the calculator is deterministic for the inputs it receives; the current quote validator does not establish that a quoted phrase describes the intended field. This report records the failure without changing application code to make the challenge pass.

01 / Data

What enters the system.

The intended users are renters comparing asking amounts and everyday amenities, and buyers inspecting estimates, sales, zoning and mapped context. The product combines three kinds of information: external property observations, explicit user responses and transparent derived values. It does not train a new valuation model.

02 / Method

Retrieve, clarify, calculate, explain.

  1. Confirm the address. A page selection produces address candidates. The user confirms the intended match before the popup's report is started. The chat separately searches addresses each turn and asks for clarification when a match is ambiguous.
  2. Retrieve the relevant data. The extension worker saves full report envelopes for Rental/Buy views. The Node chat backend uses its own smaller, allowlisted property client. The chatbot does not automatically receive the popup's saved report or notes.
  3. Collect scenario inputs. A named calculation tool declares required fields, units, ranges and enum choices. Missing fields produce needs_input. The server checks that each supplied quote appears in a user message and literally supports a number or recognized period term.
  4. Run reviewed Python. The server fetches the calculator's declared API record itself, then calls an authenticated Python endpoint. A static registry maps the calculator name to a checked-in module. Tool arguments cannot name an arbitrary URL, file path or executable script.
  5. Preserve the result and provenance. A calculation record includes metrics, units, exact inputs, API source IDs and timestamps, assumptions and module version. The chatbot explains the output; expandable details survive reopening the conversation.

Rent comparison, version 1.0.0

Let P be the proposed weekly amount in AUD, H the historical listing amount and N its confirmed periods per year: 52 for a week, 26 for a fortnight, 12 for a month or 1 for a year.

Historical weekly reference = H × N ÷ 52
Weekly difference           = P − historical weekly reference
Annual difference           = 52 × P − H × N
Percentage difference       = 100 × (52 × P − H × N) ÷ (H × N)

The Python implementation uses decimal arithmetic and rounds each final metric to two decimals using half-up rounding. It retains precision through the calculation, so an annual difference is not obtained by multiplying an already rounded weekly display by 52. Nonpositive or invalid reference prices cannot become a percentage denominator.

Suburb index

The popup averages the available five livability dimensions and rounds the final mean once. It requires a named suburb-level response and at least three valid, unique dimensions. Non-finite values, values outside 0–100 and duplicated dimensions are excluded; a legitimate zero is retained. The choice of equal weights is an explicit prototype rule, not a learned or independently validated weighting scheme.

Bounded execution

Chat keeps a 55-second overall deadline, four model rounds and six tool executions. Python calls allow up to eight seconds, reserve time for the final explanation and accept bounded JSON responses. The deployed Python function is configured for a ten-second maximum. Stop aborts the HTTP request; remote CPU work also needs its own deadline checks. Some chat list datasets are capped at 50 records, so future aggregate calculators need complete-data adapters before using those arrays.

04 / What did not work, or remains unproved

The boundaries are part of the result.

  • Semantic input binding failed one targeted challenge. A valid phrase about the proposed rent can be misapplied to the historical period. The quote validator checks literal support; it does not prove the phrase describes the intended variable. The concrete consequence is shown below.
  • The rental feed does not establish the historical amount's period. A weekly label cannot be safely inferred from a plausible-looking amount. The tool asks for clarification, but correct attribution of the answer still matters.
  • The wellbeing score is an unvalidated proxy. Its average is transparent and its missing-data behavior is tested. No study here establishes that equal weighting measures wellbeing, predicts house prices or reflects a particular user's priorities.
  • Some mockup features lack supporting data or behavior. Noise ratings, greenery measurements and nearby development applications are not invented when absent. Social links do not verify follows or unlock a free report. Sharing currently copies the confirmed address.
  • Live service quality was not measured in this evaluation. There is no accuracy/latency benchmark for address matching, valuation, API completeness, live model answers or the deployed Python route. This report does not establish that hosted compute has been configured and deployed.
  • Visual verification remains limited. A manual browser attempt during compute implementation was blocked by a browser capture failure. The chat disclosure is covered by DOM and keyboard tests; that does not substitute for a completed visual or assistive-technology review.
  • User benefit is still a product hypothesis. No controlled usability study, conversion measurement or comparison with an unaided research task was run.

05 / My held-out check

A fresh challenge after implementation.

I created the challenge after the calculation code existed and kept the evaluated application files unchanged while running it. The set is separate from existing unit-test fixtures. It is a post-implementation synthetic challenge, not a blinded independent assessment or a held-out sample of real property outcomes: the evaluator also helped implement the code.

The arithmetic reference uses exact rational numbers and integer quotient/remainder rounding. It annualizes first and does not import the production calculator or Python's Decimal for its expected values. A fixed seed, 202611071507, generates 40 new cases for each of the four periods. Five additional fixed cases cover fresh fractional amounts, a zero proposal and half-cent rounding.

The failing semantic challenge

“Proposed rent is $694.23 per week. The historical listing amount is per month.”

I supplied an adversarial tool argument with reference_period = "week", backed by the exact quote "per week". That phrase belongs to the proposal, not the historical listing. The expected behavior was rejection. The observed behavior was acceptance and a completed calculation.

With a synthetic historical amount of $2,845.37, this produced a −$2,151.14 weekly difference rather than the correct +$37.61 using the explicitly stated monthly period. The direction of the comparison reversed. This is a controlled adversarial tool-call test; it is not an observed failure rate of a live model.

Next correction: bind each confirmed value to its specific field and property in structured scenario state, display that interpretation to the user, and reject conflicts with an explicit reference-period response. Add this challenge as a regression case when implementing that change. Prompt instructions alone should not be presented as a semantic validation guarantee.

Result summary: 189 challenge cases met their expected behavior; one semantic-attribution case did not. These cases measure different properties, so combining them into a single “accuracy” percentage would be misleading.

06 / Reproduce and inspect

Keep the evidence close to the claim.

Run from the repository root with Node.js 22.12+ within 22.x and Python 3.12. Install the pinned JavaScript dependencies, then run the report's separate challenge. It uses dummy data, needs no service credentials and writes the detailed evidence file.

npm ci
python3 scripts/heldout-check.py

The script does not patch production code. Its exit status signals that the evaluation harness completed; inspect the per-category results to see product failures. The intentionally failing semantic expectation is preserved in the JSON rather than hidden behind a successful harness run. Re-running the script refreshes evidence, not this dated HTML snapshot.

  • Fresh regression, type-check and build results.
  • Reproducible challenge runner and independent rational oracle.
